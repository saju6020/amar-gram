- [MEDIUM] src/Infrastructure/AmarGram.Infrastructure/Auditing/AuditChangeCaptureInterceptor.cs:88,138 (with AuditCaptureExclusions.cs:19 and AuditRedactionRules.cs:12) — Pre-existing backend behaviour, first reached by real input once S1 sends the note. When an order is placed, the `AfterValue` snapshot therefore carries `FulfilmentDetails.RiderNote` as free text. The redaction pattern only matches secret-like property names, so the note is not redacted. Scenario: a customer writes "key under the mat, nobody home after 6, call my daughter 017…". That text can be read and exported by anyone with Audit log access (Accountant read, Administrator full; StaffRoleCatalogue.cs:50). It also survives erasure: `FulfilmentDetails.Redacted()` clears the order column (FulfilmentDetails.cs:72) but not the audit row. The same row already holds the recipient, phone and address, a class HO-ACC-001-SECURITY carries forward as "audit rows keep personal data after anonymisation". The note still breaks the rule BG-19 set for free text: AuditCaptureExclusions.cs:29-31 excludes staff notes because a DataChange row "would copy the text into the immutable audit table, where erasure could never remove it". The HO-P3 SECURITY record checked redaction of the order column only. Remediation (backend, outside S1): write `RiderNote` to audit snapshots as `"[redacted]"`, using a property-name list for customer free text, and consider `DeliveryInstructions` under the same rule. Rows already written need a separate decision. Established by reading the code; no row was observed.
- [MEDIUM] src/Api/AmarGram.Api/Modules/ShopModule.cs:87, web/lib/api/client.ts:456-460, web/lib/api/shop-catalogue.ts:201-208 — Pre-existing; S1 did not create it. The `Catalogue` rate limit (120 per minute, appsettings.json:78) is partitioned by `RemoteIpAddress`, and `getPublic` forwards no client address, so server-rendered reads from all visitors appear to share the web host's single bucket. Catalogue and product detail reads are deliberately uncached (`revalidate: 0`). Scenario: one anonymous client sends about 2 requests a second to `/shop/products?district=<anything>` (`q` or `brand` work equally), which uses up the bucket. Every visitor then gets "We couldn't load the shop" (CatalogueView.tsx:101), and product pages throw (`[slug]/page.tsx:58`) until the window resets. Ordinary traffic of 120 catalogue views a minute would do the same. `web/` has no middleware limiting this. Remediation: have the uncached server reads send the client address, with the web host configured in `RequestOrigin:TrustedProxies`; or give server-rendered reads their own authenticated allowance; or limit at the edge. A keyword search of docs/gates and docs/handover found no earlier record of this. Whether it applies depends on deployment, which I could not see (see NOT CHECKED).
