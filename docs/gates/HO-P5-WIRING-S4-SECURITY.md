FINDINGS
- [LOW] web/lib/hooks/billing/useBillingMutations.ts:265 — `setQueriesData` writes the count response into every cached cash-up read for that date, in every branch. The predicate checks only `queryKey[3] === date`, but the key is `['billing','cash-up', branchId, date]` (useBillingQueries.ts:249). An Administrator or Accountant who counts branch A and then switches to branch B for the same date first sees A's sources, expected and counted figures under B's name until the invalidation refetch answers. Inside that window `CashUpSourceCountForm` also resets its inputs to A's sources. A save is sent with B's `X-Branch-Id`. A staff key that does not exist at B is refused with `UnknownCashUpSource`. But `till` exists at both, so a till-only day could be counted against figures that belong to the other branch. The same happens if the branch switches while the PUT is in flight. This is an integrity and display issue, not a disclosure: the user is allowed to see both branches. Remediation: read `branchId` from `useBranchScope()` in `useRecordCashCount` and write only the exact key `['billing','cash-up', branchId, date]`, or match `queryKey[2] === branchId` as well. Add a case where two branches are cached on the same date.
- [LOW] web/components/back-office-customers/CustomerPasswordReset.tsx:46-57, with src/Api/AmarGram.Api/Controllers/StaffCustomersController.cs:148-161 — Nothing limits how often a reset can be sent. The button stays live after a success, so a Reception user can send one reset after another to the same customer, and each one issues a token and an SMS or email (handler :61-71). The server endpoint has no `[EnableRateLimiting]`, unlike the public reset (AuthController.cs:117,123). The harm is SMS cost and nuisance to the customer by an authenticated insider; it is not account takeover. The token goes only to the customer's own channel and is never returned (handler :76-80, mock accounts.ts:2020-2024). Each request is audited with the staff id (`InitiatedByStaffId`). The fix belongs to the backend: a per-staff and per-customer rate-limit policy on `RequestPasswordReset`, with the UI showing its 429. Optionally the UI could disable the button for the token's 15-minute life after a success. I did not raise it higher because it needs a signed-in Reception or Administrator account and leaves an audit trail.
- [LOW] web/mocks/handlers/admin/rosters.ts:346,372 (and admin/branches.ts write routes) — The new `GET …/roster-cells` and `PUT …/rosters/{id}/shifts/{date}` mocks never answer 403, but the server requires `Rosters.View` and `Rosters.Manage` (AdminRostersController.cs:50-51,73-74).
